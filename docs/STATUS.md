**За сливане от шефа (искания на авторите):**
- `src/admin/a.ts` хваща глобално `[data-ask]` (AI листа): модулите да не ползват това име или делегацията да е само в админа.
- Ядрото на шофьора да приема `at` за действията без връзка (като кухнята).
- `src/admin/a.ts` / рамката: „Потвърди и прати“ на QR от управителя е без „Отмени“ (ядрото на залата не може да го върне).
- `src/modules/routes.ts` е отделен файл (1,2 KB): +1 заявка на страниците на админа и модулите (по желание: в manualChunks).
- Демо: кратки извиквания за QR код и данни, за да е по-лесна проверката.
- „Настройки“ в админа да показва кой и кога е включил „Натоварено“ (`settings.kitchen.busyBy`, `busyAt`: вече идват от ядрото).
- „Закъснява“ в „Поръчки“ на админа вече е като в модула (готово вземане и маса не закъсняват).
- „Изчерпано“ от админа (`PUT /api/admin/menu/:id/sold-out`) и от модула на управителя да минава през `core.kitchen.setOut`, за да се отбелязват редовете на приетите поръчки.
- Смяна на статус от „Поръчки“ в админа не пипа редовете на кухнята (`ks`): да се изравни.
- Вземане „възможно най-скоро“ при „Натоварено“: сайтът обещава +20 мин, кухнята смята срок +40: едно правило.
- Модулът на управителя вика `driverApi.drivers()`, `asks()`, `answer()`, `answerUndo()`; „Финанси“ на собственика `driverApi.fuelReport()`.
- Върната от шофьора поръчка остава със статуса си (решава ресторантът); функция „пусни пак за доставка“ няма (ако трябва: въпрос към собственика 23).
- Общите текстове за права в `src/core/rights.ts` са на „вие“; в модулите на персонала те са на „ти“.

```
node scripts/make-env.mjs   # прави .env със случайни пароли и VAPID ключове (на стар .env добавя само ключовете); не е в git
npm test
npm run build && npm run serve   # http://localhost:8787
npm run build:demo               # статично демо в dist/
```

`npm run test:e2e` сам прави build в `dist-e2e/` (никога в `dist/`), пуска сървъра на порт 8788 с чиста тестова база. Акаунти на персонала: `admin`, `owner`, `manager`, `waiter`, `kitchen`, `driver`; паролите са само в `.env`.

## Уроци

- Агентите работят в отделни git копия (`git worktree add /home/user/rv-<страница>`, `node_modules` като връзка): шефът прилага разликата им (`git diff | git apply`) и комитва. Така проверка и поправки не си пречат с работата на шефа.
- Всеки агент: свой порт и свои папки за build (`dist-<име>*`, в `.gitignore`), никога `pkill` по общ шаблон.
- Шефът комитва; агентите не комитват. В комитите няма идентификатори на модели (и в редовете за авторство).
- Една сесия работи по `build/v1`; паралелни клонове по едни и същи файлове не се сливат.
- Лимитите прекъсват агентите: след нулиране се продължава същият агент (SendMessage), не нов.
- Тест, който зависи от часа на build-а или от натрупани данни, пада „случайно“: e2e тръгват с чиста база, а проверките за текст гледат само съдържанието, което тестват.
- (16.11) Средата отказва комит с ред за съавторство: комитите са без него, след всеки комит `git push origin HEAD:build/v1` (и в сесийния клон).
- (16.11) Агентите работят в отделни git копия на последния комит; шефът слива с `git diff --cached --binary HEAD | git apply --3way` и оправя само `src/admin/sections.ts` (списъка SOON). Всеки агент има свой блок портове (`docs/AGENTS.md`).
- (16.11) Админът не внася нищо ново от общия runtime на сайта: всеки нов експорт го прави по-голям на всяка страница (демото е на 25 B от бюджета).
- (16.11) Текстът, който админът въвежда, отива в статичния сайт: всичко се ескейпва, а JSON в `<script>` е с `<` (бавният тест с вредни полета: `tests/unit/menu-new-site.slow.test.ts`).
